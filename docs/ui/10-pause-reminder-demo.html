      为什么不做「真·到点静默跳过」（挂在日志里不触发）

      schedule/change 由 dsh-schedule 用 严格解码（多一个字段就抛 corrupt_schedule_log）， 且它的 runtime 只认「active 且已到点 → 派发」。任何第三方「冻结」标记都出不了两种形态： (1) 写进日志 → 宿主报错；(2) 只记在插件内存/sidecar → 关网页或重启就丢（正好是「暂停」最需要它生效的窗口）。 所以暂停只能做成「出日志」—— 也就是 delete + 插件侧留档。
      • 副作用（已实测确认）：暂停后 foldScheduleEvents 的 seenIds 会保留 s1，恢复时不能再分配 s1（allocateScheduleId 返回 s2）—— 也就是恢复后 id 会变，UI 一致但审计链看着像新建。
      • 替代做法（未采用）：用 edit（delete+create 同 id）把目标时刻改到很远的未来。缺点：日志里的时刻被篡改、面板会显示「1000 小时后」、恢复时又得再 edit 一次，语义含混。

      方案 A 的推荐落地形态 推荐

      动词拆成两条命令，纯 host、零 UI 阻塞：
      /user-schedule-pause {"{id}"} → 返回 {"{ok,id,remaining_seconds,scheduled_at}"}，host 把 {prompt, at/after, delivery} 存进 sidecar
      /user-schedule-resume {"{id}"} → 重建任务并把新 id 回给客户端（同位替换 dock 行并解冻进度条）
      UI 定稿：原地冻结、不拆分区——暂停后行留在 dock 原位，进度条停在冻结宽度并呈条纹，文案改「已暂停」；投影需把 paused[] 并入 wire（stateVersion: 4），否则 delete 后行会消失。
